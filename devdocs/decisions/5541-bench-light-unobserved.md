# 5541: bench flags lanes with no `light` field

- **Cause (bench config).** The bench ran with the fast path switched off, so `light` was never decided. The run config set the sandbox `forge.yaml` to `lean.light.mode: off` (`docs/eval/adversarial-bench.md:23`), and the published run says "light lane off" (`docs/eval/published/adversarial-2026-11-11.md:16`). With mode off, `lean.mjs:2067` emits no eligibility event, so those lanes have no `FASTFORWARD_ELIGIBILITY` event. That absence is the citation. It was not an eligibility verdict (no `eligible:false` event), and `lean.light.source` was never reached.
- **Cause (events).** The engine always writes a boolean `light` into the result (`bin/lean/lean.mjs:563`, `let light = false` at :424), so a `null` in the bench row means the result file was not read (no `--result-file`) or an older engine wrote none. It is not an eligibility verdict. When the file is read, `light:false` on a valid lane has these event traces: `lean.light.mode: off` emits no eligibility event (`lean.mjs:2067` gates on mode); the default `shadow` emits `LIGHT_ELIGIBILITY` (`lean.mjs:2065`, text source) or, with `lean.light.source: investigation`, `FASTFORWARD_ELIGIBILITY` with `shadow: true` (`lean.mjs:2156`, `bin/lean/fastforward.mjs:92`) and runs the normal full lane; only `mode: on` fast-forwards. A bench lane with no FASTFORWARD_ELIGIBILITY event therefore ran with mode off, or with source `text`; one with `shadow: true` ran in shadow. Read them with `stats --depth` (`bin/stats/depth.mjs:62`).
- **Change.** `bench-lightlane.mjs` marks `light_unobserved`; `bench-adversarial.mjs` counts it per arm in the scorecard. Engine and the duplicate rule are unchanged.
- **Corpus.** `adv-int-take-until` aliased the existing `takewhile_inclusive`, so closing it was correct; replaced by `adv-int-is-permutation`. The first swap tried `argmax`, but that also ships at the base (`more_itertools/more.py:5340`, `docs/api.rst:169` @670b715), so it was dropped. No `is_permutation` exists there (only `iequals`, which checks order, and `distinct_permutations`). Note: `adv-int-minmax-by` likewise maps onto `minmax(..., key=)`. It is outside this issue and left for a follow-up.
- **Deferred.** The ≤ 1.3× cost re-run on legion with `lean.light.mode: on`.
- **R2 post-deploy.** The cost re-run needs the legion host and paid spend, so it is post-deploy: check `adversarial-bench-light-cost-1.3x` in `.forge/post-deploy-checks.json` reads the newest published scorecard (full cost ≤ 1.3× control, oracle pass rate not lower). `docs/eval/adversarial-bench.md` now tells the bench to run with `lean.light.mode: on`.
